Visão geral

A Rafael Orizio é um projeto de engenharia de dados que centraliza informações de dois CRMs — Dolibarr (MySQL) e Invoice Ninja (exportações CSV) — em um Data Warehouse PostgreSQL. O pipeline é orquestrado pelo Apache Airflow, as transformações são feitas em Python/Pandas e o consumo analítico acontece no Metabase.

O objetivo é entregar uma visão única de faturamento, recebimentos, saldo em aberto e clientes, com execução diária, carga idempotente e documentação versionada.

O conjunto de exemplo atual possui 12 faturas de 2 clientes, emitidas entre julho e novembro de 2026, totalizando R$ 535.122,94 em faturamento e R$ 125.519,42 em aberto.

Integração

Duas origens de CRM convergindo para um modelo analítico comum.

02

Confiabilidade

Agendamento diário, retries, upsert por chave de negócio e logs por tarefa.

03

Analytics

Camada de BI com perguntas reutilizáveis, filtros e dashboards executivos.

!

Nota de escopo. O docstring original das DAGs menciona o Databricks como destino. A implementação atual entrega os dados no PostgreSQL e é consumida pelo Metabase. O Databricks permanece como evolução possível no roadmap.

Arquitetura

O desenho segue um fluxo ETL em lote. Cada origem tem uma DAG dedicada, mas ambas compartilham a mesma tabela fato e a mesma estratégia de carga.

Fluxo de dados
Dolibarr (MySQL 10.89.0.8)
        \
         \  acctech_dl1  →  Pandas  →  PostgreSQL (192.168.0.100)
         /                                   │
        /                                    ▼
Invoice Ninja (CSV)                      Metabase
         \  acctech_dl2  →  Pandas  →  DH_INVOICES  →  Dashboards

Camadas

CamadaTecnologiaResponsabilidade
OrigensMySQL · CSVDados transacionais de faturas e clientes
OrquestraçãoApache AirflowAgendamento, dependências, retries e observabilidade
ProcessamentoPython · PandasLimpeza, padronização, merge e regras de negócio
ArmazenamentoPostgreSQLTabela fato DH_INVOICES (camada analítica)
ConsumoMetabasePerguntas, dashboards, filtros, alertas e assinaturas

Decisões de projeto

  • Uma tabela fato única: simplifica o consumo e permite comparar as duas origens.
  • Prefixo INV- nas referências do Invoice Ninja: evita colisão com referências do Dolibarr na chave primária.
  • Upsert pela chave dl_st_ref: torna as execuções repetíveis e idempotentes.
  • Transformação no próprio Airflow: reduz a infraestrutura necessária nesta fase do projeto.
  • SQL transparente no Metabase: as regras analíticas ficam auditáveis e versionáveis na documentação.

Configuração do ambiente

1. Clonar o repositório

Shell
git clone https://github.com/SEU-USUARIO/DE_CRM_Metabase_Airflow.git
cd DE_CRM_Metabase_Airflow

2. Iniciar o Airflow

Com Astro CLI:

Shell
astro dev start

Ou utilize o Docker Compose/ambiente Airflow já provisionado pela sua equipe.

3. Disponibilizar os CSVs

As DAGs usam os caminhos definidos no topo do arquivo e expandem ~ com os.path.expanduser(). Crie o diretório e copie os arquivos:

Shell
mkdir -p "$HOME/airflow/include/data"
cp airflow/include/data/invoices.csv "$HOME/airflow/include/data/"
cp airflow/include/data/clients.csv  "$HOME/airflow/include/data/"

# Verifique o caminho resolvido
python -c "import os; print(os.path.expanduser('~/airflow/include/data/invoices.csv'))"
i

No Astro Runtime, o diretório de includes costuma ser /usr/local/airflow/include/data. Confirme o HOME do usuário que executa o scheduler/worker e ajuste os caminhos se necessário. O importante é que o arquivo exista no filesystem de todos os componentes que executam a tarefa.

4. Validar a importação das DAGs

Shell
airflow dags list | grep acctech
airflow dags list-import-errors

DAGs e tarefas

Ambas as DAGs iniciam em 2026-08-03, têm agendamento @daily, retries=3 e owner Rafael Orizio. As tarefas são implementadas com PythonOperator e se comunicam via XCom.

DAGTarefasFonteDestino
acctech_dl1extract_mysql → transform_data → load_postgresDolibarr MySQLDH_INVOICES
acctech_dl2read_from_csv → transform_data → load_postgresInvoice Ninja CSVDH_INVOICES

As transformações gravam um CSV temporário exclusivo por execução em /tmp e passam apenas o caminho via XCom para a carga. Isso evita colisão quando as duas DAGs executam ao mesmo tempo.

!

Atenção ao volume. O dataset ainda é passado entre as etapas de extração e transformação via XCom. Para volumes maiores, recomenda-se persistir em staging (arquivo, S3 ou tabela temporária) e passar apenas o caminho/referência. Esse item está no roadmap.

DL1 · Dolibarr para PostgreSQL

A DAG acctech_dl1 extrai faturas e clientes do MySQL, exclui faturas abandonadas (fk_statut = 3) e carrega o resultado na tabela fato.

Consulta de extração

SQL · MySQL
SELECT  fac.ref,
        fac.datef,
        fac.date_lim_reglement,
        fac.total_ht,
        soc.code_client,
        soc.nom,
        soc.idprof4,
        soc.multicurrency_code,
        fac.tms AS facture_tms,
        soc.tms AS customer_tms
FROM dolibarr.llx_facture fac
INNER JOIN dolibarr.llx_societe soc ON soc.rowid = fac.fk_soc
WHERE fac.fk_statut <> 3;

Transformação

  • Remove espaços e converte a referência para maiúsculas.
  • Converte datef e date_lim_reglement para datetime.
  • Adiciona processed_at em UTC.
  • Renomeia as colunas para o padrão dl_* da tabela fato.
  • Salva um CSV temporário em /tmp/transformed_data.csv para a carga.

Carga

A carga cria DH_INVOICES se não existir e executa insert_rows com replace=True e replace_index=["dl_st_ref"] — um upsert pela chave primária.

Python · trecho da carga
postgres_hook.insert_rows(
    table=target_table,
    rows=rows,
    target_fields=df.columns.tolist(),
    replace=True,
    replace_index=["dl_st_ref"]
)

DL2 · Invoice Ninja para PostgreSQL

A DAG acctech_dl2 lê invoices.csv e clients.csv, seleciona as colunas relevantes e enriquece as faturas com Number (código do cliente) e ID Number (documento) por meio de um merge em Client Name.

Regras aplicadas

  • Normaliza valores no formato brasileiro: remove separador de milhar e troca vírgula por ponto.
  • Converte Invoice Amount e Invoice Balance para float.
  • Prefixa o número da fatura com INV-.
  • Copia Invoice Date para dl_ts_facture_tms.
  • Adiciona processed_at em UTC.
  • Renomeia as colunas para o padrão dl_*.
Python · normalização monetária
df["Invoice Amount"] = (
    df["Invoice Amount"]
      .str.replace(".", "", regex=False)
      .str.replace(",", ".", regex=False)
      .astype(float)
)
!

O merge usa how="left": faturas sem cliente correspondente permanecem no dataset, mas com campos de cliente nulos. Monitore esses casos para identificar divergências de cadastro entre os sistemas.

Nos CSVs atuais: os nomes estão padronizados (AirFrance e TAP), e as 12/12 faturas encontram cliente no merge. Mantenha essa validação sempre que os arquivos forem atualizados.

Transformações e padrões

As duas DAGs convergem para o mesmo contrato de dados. O padrão de nomes segue a convenção dl_<tipo>_<atributo>:

  • dl_st_*: strings.
  • dl_dt_*: datas de negócio.
  • dl_dc_*: valores decimais/monetários.
  • dl_ts_*: timestamps de origem.

Essa padronização facilita o consumo no Metabase e reduz o acoplamento da camada de BI com os nomes originais de cada CRM.

Modelo de dados

A tabela DH_INVOICES é criada automaticamente pela carga caso não exista. Como o nome é criado sem aspas, o PostgreSQL o armazena em minúsculas (dh_invoices); consultas sem aspas funcionam normalmente.

Consultas de validação

SQL · PostgreSQL
-- Volume e valores consolidados
SELECT
  COUNT(*) AS faturas,
  SUM(dl_dc_total) AS total_faturado,
  SUM(COALESCE(dl_dc_balance, 0)) AS saldo_aberto
FROM DH_INVOICES;

-- Duplicidades na chave de negócio
SELECT dl_st_ref, COUNT(*) AS ocorrencias
FROM DH_INVOICES
GROUP BY dl_st_ref
HAVING COUNT(*) > 1;

-- Registros recentemente processados
SELECT MAX(processed_at) AS ultima_carga
FROM DH_INVOICES;

Qualidade de dados

As validações abaixo podem ser executadas após cada carga ou evoluídas para testes automatizados no Airflow (por exemplo, com SQLCheckOperator).

RegraVerificaçãoAção recomendada
Unicidadedl_st_ref não pode duplicarUpsert já garante; monitorar violações
Obrigatoriedadedl_st_ref, dl_st_customer preenchidosFalhar a tarefa ou registrar ocorrência
Valoresdl_dc_total >= 0Investigar estornos e lançamentos manuais
Coerênciadl_dc_balance <= dl_dc_totalRevisar regra de negócio da origem
DatasEmissão e vencimento parseáveisCorrigir formato na origem
MoedaCódigo com 3 letras (ex.: BRL)Padronizar cadastro
RelacionamentoToda fatura com cliente identificávelTratar merge à esquerda nulo
Correspondência de nomesClient Name da fatura deve casar com Name do clienteValidar a cada carga; hoje 12/12 faturas têm match
!

dl_dc_balance só é preenchido pela DAG do Invoice Ninja. Faturas vindas do Dolibarr ficam com saldo nulo. No Metabase, use COALESCE(dl_dc_balance, 0) e documente essa diferença ao analisar recebíveis.

O que monitorar

  • Duração das tarefas e falhas após retries.
  • Quantidade de registros extraídos, transformados e carregados.

  • Crescimento da tabela e tempo de resposta das consultas do Metabase.

Segurança

  • Credenciais somente no Airflow/secrets backend, nunca no código.
  • Usuários de banco com privilégio mínimo: leitura no MySQL e escrita restrita ao schema do DW.
  • Metabase com usuários e grupos separados por necessidade de acesso.
  • Conexões preferencialmente em rede privada/VPN; habilite SSL quando disponível.
  • Dados pessoais e documentos fiscais devem seguir a política de retenção da empresa.
  • Revisar permissões de leitura dos CSVs no runtime do Airflow.

Troubleshooting

DAG não aparece ou erro de importação

  • Confirme os providers instalados no ambiente do scheduler.
  • Rode airflow dags list-import-errors.
  • Verifique compatibilidade entre a versão do Airflow e o uso de airflow.sdk.

Arquivo CSV não encontrado

  • Execute python -c "import os; print(os.path.expanduser('~/airflow/include/data/invoices.csv'))".
  • Garanta que o arquivo exista no mesmo host/container do worker.
  • Verifique permissões de leitura do usuário do Airflow.

Erro de conversão monetária

  • Inspecione valores vazios, símbolos de moeda ou formatos inesperados.
  • Garanta que o CSV seja exportado no padrão brasileiro esperado pela DAG.

Falha de conexão com os bancos

  • Teste a conexão pela UI do Airflow.
  • Confirme host, porta, schema, usuário, senha e regras de firewall.
  • Verifique se o driver (psycopg2/MySQLdb) está instalado.

Metabase não mostra a tabela

  • Em Admin → Databases, sincronize o schema novamente.
  • Confirme o schema correto e as permissões do usuário do Metabase.
  • Use DH_INVOICES ou dh_invoices sem aspas.

XCom muito grande

  • Reduza o volume por execução ou persista o dataset em staging.
  • Não é recomendado transportar grandes listas de dicionários via XCom.

Limitações e roadmap

Limitações atuais

  • Carga full/upsert diário, sem watermark incremental por data de atualização.
  • Dataset trafega via XCom entre tarefas.
  • Saldo em aberto disponível apenas para a origem Invoice Ninja.
  • Tabela fato não possui status da fatura nem datas de pagamento detalhadas.
  • CSVs são atualizados manualmente no repositório/runtime.
  • Sem testes automatizados de qualidade ou CI para as DAGs.

Próximos passos

  • Adicionar camada de staging e carga incremental por watermark.
  • Implementar testes de dados no Airflow e validações de schema.
  • Evoluir para modelos dbt (staging, intermediate e marts).
  • Adicionar status, datas de pagamento e aging calculado na origem.
  • Integrar Databricks/Delta Lake como camada analítica, conforme visão original.
  • Configurar alertas de falha e assinaturas de dashboard no Metabase.
  • Publicar pipelines com CI/CD e documentação automática.
